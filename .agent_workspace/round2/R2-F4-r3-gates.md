# R2-F4 Round 3 独立评审验收包（R3 Gates & 剩余差距）

- **子代理**：R2-F4（fable）｜Round 2 / 10 代理（4 fable + 3 opus-fast + 3 gpt-sol）
- **日期**：2026-08-28
- **输入**：`ROUND1_BRIEF.md`、`round1/R1-F2-audit-acceptance.md`（Gate 编号权威来源）、`LEGAL.md`、`MASTER_PLAN.md`、`round2/DISPATCH.md`
- **用途**：Round 3 父调度器据此对 Round 2 产出做**独立复审**。本文回答三件事：
  1. 哪些工件必须存在（存在性即 Gate，缺失即 FAIL）；
  2. 法务扫描如何**默认拒绝（fail-closed）**地执行；
  3. 用什么量表把"规划完备度"与"实现完备度"**分开打分**，避免用漂亮的计划掩盖单薄的代码，也避免用"还没有 GUI"抹杀已冻结的计量规范。

## 0. 诚实声明（先说结论，防止评审预期错位）

**Round 2 不可能、也不应该交付 VIC 级 GUI。** 理由是结构性的，不是执行不力：

1. VIC 的公开产品形态是"采集（VIC-Snap）+ 标定 + 相关 + 应变 + 实时（VIC-Gauge）+ 可视化（iris）+ Python（vicpyx）+ 报告 + Windows 安装与许可"的整条测量链（见 `PROGRESS.md` 关键发现 2）。其中采集与实时依赖真实相机硬件，GUI 打磨依赖长期交互迭代与 beta 用户反馈——这些在本 CPU-only、无 GUI 会话、无相机的 Linux 云环境内没有验证回路。
2. 我们从未合法运行过 VIC 的 UI（`LEGAL.md`：Windows 评估闭环在本环境不可合法完成），所以连"对齐 VIC UI"的基准都不存在（Round 1 遗留缺陷 5）。声称做出了"VIC 级 GUI"本身就无法通过 R3-04 声明一致性检查。
3. Round 2 派工单（`round2/DISPATCH.md`）的实现项就只有：CPU 一阶 ICGN 最小内核、立体标定/三角化轻量实现、HDF5 schema 与骨架、基准脚本、CI 探针。这是**测量链的地基**，不是产品。

因此 Round 3 的正确评审姿势是：**规划完备度按"超越 VIC 的完整路径"满分线打，实现完备度按"地基里程碑"满分线打，两轴分开，禁止互相折算。** 任何文档若宣称 GUI/实时/相机生态"已完成"，按第 3 节 L-6 判定为声明造假，整体 FAIL。

## 2. Fail-closed 法务扫描（L 系列）

原则：**默认拒绝**。扫描器跑不起来、结果不可读、来源说不清，一律按 FAIL 处理，而不是"没扫到问题就算过"。这与 R1-F2 的 R3-08 同源，但收紧为 Round 2 仓库现实可执行的版本。

### 2.1 扫描项

| # | 扫描项 | 方法（评审机可复现命令示例） | FAIL 判据（任一命中即 FAIL） |
|---|--------|------|------|
| L-1 | VIC 二进制/安装包 | 全仓查找 PE/MSI/大文件：`rg --files \| xargs -I{} file {} \| grep -Ei 'PE32\|MSI\|installer'`；另列出 >10 MB 文件逐一说明来源 | 存在任何 Windows 可执行体/安装包；存在无来源说明的大二进制 |
| L-2 | 专有字符串/逆向痕迹 | `rg -i -n '(\.z3d\|vic-snap\|vic-gauge\|keygen\|crack\|license.{0,10}bypass\|patch.{0,10}serial)' --hidden` 于 `src/ tests/ benchmarks/ docs/` | 代码/测试/脚本中出现专有工程格式解析、许可绕过、密钥生成相关内容。**白名单**：`.agent_workspace/` 与 `docs/` 中作为"竞品公开信息引用/禁止事项说明"出现的词条（如本文件），须在白名单文件 `legal/scan-allowlist.txt` 中逐条登记路径+行号+理由；未登记的命中一律 FAIL |
| L-3 | 专有手册文本污染 | 抽查 `src/` 全部注释与 docstring：算法描述必须引用公开文献编号（论文 DOI / GPG 条款号 / 开源仓库+许可证），不得出现"VIC 内部如何做"的表述 | 任何注释声称来自 VIC 手册/二进制行为观察；任何无出处的"厂商实现细节" |
| L-4 | 依赖许可证矩阵（SBOM） | `pip list` / 锁文件逐项核对许可证；对照 E-2 的 ADR 选型 | 存在与 ADR 不兼容的依赖（例如 ADR 选宽松许可而引入了强 copyleft 运行时依赖）；存在**无许可证**仓库的代码拷贝（LEGAL.md：无许可证仓库只读论文）。OpenCorr 代码拷贝 = 直接 FAIL（裁决为独立实现） |
| L-5 | 数据集入库检查 | 检查 Challenge 等数据集是否被提交进 git；应只有 SHA256 manifest + 下载脚本 | 数据集本体入库且无许可条款快照；manifest 缺失但数据已被脚本默认下载到仓库内 |
| L-6 | 声明一致性（法务侧） | 抽查全部 round2 报告与 PRD 中的对比性陈述 | 出现"我们实测优于 VIC"类陈述而证据仅为厂商宣传值或根本无 metrics.json；出现"已对齐 VIC UI"类陈述（我们从未合法见过其 UI）；出现未标注协议的吞吐数字（违反 ROUND1_BRIEF 缺陷 3 的裁决） |
| L-7 | 显微镜模块零代码 | `rg -i -n '(microscop\|远心畸变校正实现\|US7133570)' src/ tests/` | `src/` 中存在显微镜畸变**实现**代码（检索清单、法务记录不算）；FTO 未出书面结论前该项永久 fail-closed |

### 2.2 Fail-closed 执行规则

1. **扫描器缺失即 FAIL**：评审机上 `rg`/`file`/`sha256sum` 任一不可用且无等价替代记录，L 系列整体判 FAIL，先修评审环境再评。
2. **白名单显式化**：一切豁免必须写进 `legal/scan-allowlist.txt`（路径 + 模式 + 理由 + 登记人），随仓库版本化。口头豁免无效。评审时白名单本身也要人工抽查——豁免理由站不住的按未豁免处理。
3. **不可判定即 FAIL**：任何文件来源、许可证、文献出处说不清楚的，不做善意推定。
4. **一票否决**：L-1、L-2（未白名单命中）、L-4（OpenCorr 拷贝）、L-6、L-7 任一 FAIL → Round 2 整体不通过，与 R1-F2 裁决规则（R3-08 一票否决）保持一致。
5. **留痕**：扫描命令、输出、白名单版本、判定人写入 `round3/` 评审记录，供第三方复核。

## 3. 双轴评分量表（0–5）：规划完备度 vs 实现完备度

### 3.1 为什么必须双轴

单轴打分会产生两种系统性谎言：把 500 页规划打成"接近完成"（实为 0 行可用代码），或把"还没有 GUI"打成"项目失败"（实为地基按计划冻结）。因此：

- **轴 A（规划完备度）**：满分线 = "存在一条可审计、可执行、法律干净的完整路径，使 HL3 在整条测量链上超越 VIC"。评的是路径质量，不是路径已走完。
- **轴 B（实现完备度）**：满分线 = R1-F2 §2 的 v1 列（含 GUI、实时、相机生态）。**这条满分线在本三轮任务内不可达，且这是设计事实而非缺陷**；Round 2 的诚实靶位是 B=2，冲 B=3。
- **禁止折算**：A 与 B 不加权合成单一总分。对外汇报必须并列报两个数。

### 3.2 轴 A：超越 VIC 的规划完备度（0–5）

| 分值 | 锚定描述（须全部满足本档条目才可得该档分） |
|------|------|
| **0** | 无统一计划，或计划与 VIC 公开基线（`research/vic_public_feature_baseline.md`）无对照关系。 |
| **1** | 有多份规划文档但相互冲突未消解（= Round 1 结束态：许可证三说、吞吐三个数、全局 DIC 边界未定）。 |
| **2** | ROUND1_BRIEF §2 的 7 条冲突已由唯一裁决消解；`MASTER_PLAN.md` 单一有效；许可证 ADR 存在（E-1、E-2 通过）。 |
| **3** | 每条超越楔子（跨平台、Python-first、UQ 默认开、GPU 基准、open-core、双内核、公开 schema）都映射到编号 Gate（G2D-*/G3D-*/GP-*）；吞吐等数字全部带协议与硬件口径或标注 `[工程判断]`；基准协议（R1-G2）与 Gate 台账打通。 |
| **4** | 在 3 之上：Challenge 数据回归协议、UQ 校准、GPG Ed.2 条款→功能映射、法务红线全部纳入计划并互相引用无矛盾；交叉审计（E-12）确认无遗留高危冲突；不可在本环境验证的项（GUI 对标、GPU 吞吐、Windows 评估）**每一项都有明确的后续验证窗口与责任方**（用户侧持证走查协议、GPU 基准机方案），而不是被沉默略过。 |
| **5** | 在 4 之上：每个 Gate 有 claims-to-evidence 追踪表与 Round 3 可执行的最小复现命令；风险登记（R1–R10 类）逐条有缓解状态；计划本身通过了"第三方从干净克隆读一遍就能接手执行"的走查。 |

### 3.3 轴 B：实现完备度（0–5）

| 分值 | 锚定描述 | 与本任务的关系 |
|------|------|------|
| **0** | 无可运行代码。 | — |
| **1** | 仅辅助脚本（合成散斑生成器等），无相关器（= Round 1 结束态）。 | 已越过 |
| **2** | CPU 一阶 2D ICGN 内核在干净克隆可装、可跑；单测全绿（E-3、E-4）；对 `synth_speckle.py` 合成平移的 bias 实测落盘 `metrics.json`（E-8），量级达到 ROUND1_BRIEF 目标（0.01 px 级，本轮先跑通再收紧）。 | **Round 2 及格线** |
| **3** | 在 2 之上：立体标定+三角化轻量实现闭环（E-5 实现档）；HDF5 schema 冻结且内核输出遵循之（E-6）；噪声底 + 插值 S 曲线基准入 CI 且可复跑（E-9、E-10）。 | **Round 2 理想线** |
| **4** | 2D/3D 全链（标定→相关→应变→HDF5 导出）headless 可跑；Challenge 冒烟子集回归绿；UQ 噪声底一键化（GP-1 MVP 档）。 | 超出 Round 2 派工范围；Round 3 若达成属超额，**不得**因未达成而追责 Round 2 |

### 3.4 打分程序（防作弊条款）

1. **证据先行**：每个分值判定必须引用工件路径（E 系列编号或文件路径 + 行号）。无路径引用的分数无效，按下一档取（fail-closed 同样适用于打分）。
2. **就低不就高**：档位描述中任何一条不满足，即落到下一档；不允许"基本满足给 3.5"这类内插——量表只有整数档。
3. **双人独立**：Round 3 由父调度器指定 2 个互不通气的评审子代理各打一遍，分差 ≥2 档时必须书面对质并留痕。
4. **预期区间公示**：按本文 §0 与派工单，Round 2 结束的诚实预期是 **A ∈ [4,5]，B ∈ [2,3]**。若任何报告自评 B ≥ 4，先查 L-6。

### 3.5 通过线（Round 2 → Round 3 放行判据）

- **硬门**：E-1/E-2/E-3/E-4/E-8 全 PASS，且 L 系列一票否决项零命中。
- **分数线**：A ≥ 4 且 B ≥ 2。
- **B = 2 时的附加义务**：未达 B=3 的缺口（立体实现档位、schema 落地、CI 集成）必须逐条写入 Round 3 派工单，不许静默降格为"以后再说"。

## 5. Round 3 评审执行顺序（一页流程）

1. 干净克隆 → 跑 E 系列存在性检查（脚本化，输出 PASS/FAIL 表）。硬门 FAIL → 中止，出整改单。
2. 跑 L 系列法务扫描（fail-closed，白名单核查在前）。一票否决命中 → 中止。
3. 复跑 E-9 基准，diff metrics.json（<1%，确定性模式为 0）。
4. 两名评审独立按 §3 打 A/B 双轴分，附证据路径。
5. 汇总：硬门 + 分数线判定放行与否；把 B 档缺口与 GAP 台账写进 Round 3 派工单与对外声明模板。
